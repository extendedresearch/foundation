# Toolchain and dependency pins

Four pins, each held for a different reason. Three of them fail loudly when a
package gets them wrong; one fails silently, which is why it is written as an
exact version rather than a range.

| Pin | Requirement | What goes wrong without it |
|---|---|---|
| cbindgen | `=0.29.4` | A regenerated header differs from the committed one in formatting alone, and the drift check that catches real changes cries wolf |
| pyo3 | `0.29`, with `abi3-py311` | `pyo3-ffi` declares `links = "python"`, so a second series is a resolution error |
| napi, napi-derive | `3` | `napi-sys` declares no `links`, so a second series builds, and the types do not match |
| Rust | 1.85 | Edition 2024 does not compile on anything earlier |

## cbindgen is pinned to an exact version

```toml
cbindgen = "=0.29.4"
```

A header generated by cbindgen is committed, and a CI job regenerates it and
compares. That check is worth having only while every failure it reports is a
change to the C contract.

cbindgen's output layout is not part of its API, and two versions of it emit the
same declarations with different blank lines, different comment placement and a
different ordering of items whose relative order is unconstrained. A caret
requirement (`"0.29"`) lets a CI runner pick up a patch release the author never
ran, and the drift job then fails on a diff that changes no declaration.

What that costs is not the one red build. It is that the next person to see the
job fail has been taught, by a failure that turned out to mean nothing, that
this job means nothing — and the failure after that one, the real one, is
re-run until it goes away or dismissed as the formatter again. An exact
requirement removes the category: every diff the job reports is a declaration
that moved.

The cost of the exact pin is that a cbindgen upgrade is a deliberate commit that
regenerates the header in the same change. That is the intended shape of the
work.

**Nothing in this repository generates a header** — `extendedresearch-abi`
exports no `extern "C"` symbol — so the pin is stated here and enforced in each
consuming package's own manifest and drift job. There is no check here that
would catch a package using a different version.

## pyo3 moves in lockstep, and says so

```toml
pyo3 = { version = "0.29", features = ["abi3-py311"] }
```

`pyo3-ffi` declares `links = "python"`, and Cargo permits exactly one package
with a given `links` value in a build graph. A consumer whose pyo3 requirement
resolves to a different minor series than `extendedresearch-pyo3`'s fails to
resolve — a message naming both versions, before anything compiles.

That is the good case. The failure is at the earliest possible point, it names
the two requirements, and no wrong artefact is produced.

`abi3-py311` builds against the stable ABI from Python 3.11 upward, so one
wheel serves 3.11, 3.12 and 3.13 rather than one per minor version.
`extension-module` is deliberately not enabled here: it belongs to the
consumer's `cdylib`, which is where the decision about how the module links is
made, and enabling it in a shared crate stops that crate's own tests from
linking an interpreter.

Check, in the consumer:

```bash
cargo tree -i pyo3-ffi    # exactly one version
```

## napi moves in lockstep, and does not say so

```toml
napi = { version = "3", default-features = false, features = ["napi6"] }
napi-derive = "3"
```

`napi-sys` declares no `links` value. Cargo therefore has no reason to refuse a
second major series, and builds both: the consumer links its own `napi` beside
this crate's, and the two agree about nothing that crosses between them. A
`napi::Error` constructed here is a different type from the consumer's
`napi::Error`, so the error protocol in
[error-tokens.md](error-tokens.md) stops working while every crate compiles.

There is no resolution error to read and no linker error to read. The first
symptom is a runtime one, in the binding, where the failure looks like a bug in
the error translation.

So the requirement is repeated in every consuming manifest, and checked there:

```bash
cargo tree -i napi        # exactly one version
```

The consumer also names `napi` and `napi-derive` in its own manifest whether or
not it mentions them in its source, because the export macros expand to
`#[napi]` items in the consumer's crate and the code `napi-derive` generates
refers to `napi` by that name.

## The MSRV is 1.85

`rust-version = "1.85"` in `[workspace.package]`.

1.85 is the release that stabilised edition 2024, and the workspace is on
edition 2024. The floor is the edition's, not a dependency's: pyo3 0.29
declares 1.83 and napi 3 declares 1.82, both below it, so neither raises it.

A consumer on a newer toolchain is unaffected. A consumer on an older one could
not compile an edition-2024 crate at all, whatever `rust-version` said.

`rust-version` is a promise, and a promise nothing exercises drifts: an API
stabilised after 1.85, used by accident, compiles on stable and fails only for
whoever pinned the older toolchain. The `msrv` job in `.github/workflows/ci.yml`
is what holds it — the whole suite on 1.85, not a build:

```bash
cargo +1.85 test --workspace
```
